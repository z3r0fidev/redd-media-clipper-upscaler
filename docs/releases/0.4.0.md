## Summary

A third clip mode, **smart**, makes frame-exact clips that keep the source's quality in the
middle and are made almost as quickly as fast-mode clips. It re-encodes only the partial groups of
pictures at each end of the range, stream-copies every whole GOP in between, joins the parts and
checks the seams before the clip is saved. Videos it cannot handle safely are cut in accurate
mode instead, with a reason, so a smart clip never fails where an accurate one would have worked.
It works from `rmedia clip`, `rmedia batch`, manifests and a new **Smart** mode in the desktop
app, which also shows keyframe markers and the copied and re-encoded parts on the timeline.

## New Features

- **`--mode smart`** on `clip` and `batch`. H.264 (Baseline, Main or High, 8-bit 4:2:0,
  progressive, constant frame rate) in mp4, mov, mkv or ts. The start and end land on the frames
  you asked for (±1 frame), the copied frames are identical to the source's, and the result line
  says how much was copied: `(smart, 92% copied)`. Only the video is smart-cut; the audio and
  other streams are cut as accurate mode cuts them. See the
  [CLI Reference](../api/cli-reference.md#smart-mode).
- **Automatic fallback with a reason.** A source or range that smart cut cannot handle is cut in
  accurate mode with the warning `smart cut not possible: <reason>; cutting in accurate mode`
  (`SMART_FALLBACK`). There are 12 stable reason codes, from `codec` and `vfr` to `open_gop`,
  `no_full_gop` and, after the join, `params_changed` and `seam_check`
  ([Smart Cut Codes](../reference/smart-cut-codes.md),
  [Troubleshooting](../user/troubleshooting.md#smart-cut)).
- **Strict mode.** `--no-smart-fallback` (manifest `smart_fallback: false`, **Only smart** in the
  app) makes a fallback an error: exit 3 before anything runs, or a failed clip (exit 1) when the
  seam check fails (`SMART_UNAVAILABLE`).
- **Seam check.** After the join, rmedia counts the frames, checks the frame step, and decodes
  around each seam: no decode errors, every frame the source's size, and the copied frames'
  hashes equal to the source's. A clip that fails is never kept; it is redone in accurate mode.
- **Dry run.** `--dry-run` prints each job's parts,
  `smart: head 0.680 s (17 fr) re-encoded · copy 16.000 s (400 fr) · tail 0.720 s (18 fr) re-encoded · 92% copied`,
  or `smart → accurate: <reason>`, and a batch ends with
  `smart: 3 jobs; fallback: 2 (open_gop 1, vfr 1)`. `--dry-run --json` shows the five commands
  each smart job runs.
- **Manifests.** `mode: "smart"` and `smart_fallback` in JSON manifests at every level, and the
  CSV columns `mode` and `smart_fallback`. The desktop app's exports keep them, and `rmedia batch`
  on an export gives the same files as the app
  ([File Formats](../api/file-formats.md#smart-cut-in-manifests)).
- **Desktop app.** **Smart (frame-exact, copies most of the video)** as a mode for one video or as
  the default in Settings; keyframe ticks on the timeline, loaded in the background (all 300 of a
  10-minute video's keyframes appeared within 1.5 s); green and orange bands for the copied and
  re-encoded parts of the marked range, with the copied share or the fallback reason under the
  timeline; **Only smart (no fallback)** per video and a **Smart** / **Smart only** switch per
  clip; **Smart · 92% copied** or **Accurate (smart fallback: …)** in the run panel; and the
  doctor line in Settings ([Desktop App Guide](../user/desktop-guide.md#smart-mode)).
- **`rmedia doctor`** reports `smart cut: available (libx264)`, or `unavailable — <reason>`; the
  JSON gains `"smart": {"available", "reason"}`.

## Enhancements

- JSON output, all additive: a `smart` block on smart jobs (parts, frames, copied share,
  fallback) with `cwd` and `pipeline`, `smart` totals on the plan, `detail.reason` on issues,
  notices and `job_warning` events, the stages `head`, `copy`, `tail`, `audio`, `join` and
  `verify`, and a `smart` block on the clip outcome
  ([JSON Output › Smart cut](../api/json-output.md#smart-cut)).
- New issue codes: `SMART_FALLBACK`, `SMART_UNAVAILABLE` and `SMART_NOT_APPLIED` (smart was asked
  for a job that upscales or makes a GIF, which re-encodes every frame anyway).
- Desktop IPC: `keyframes` / `cancel_keyframes` (cached per file, size and modification time) and
  `smart_plan` ([Desktop IPC](../api/desktop-ipc.md)).
- Settings: `defaults.mode` accepts `"smart"`, and `defaults.smart_fallback` is new
  ([Configuration](../administration/configuration.md)).
- The scan benchmark reports its time on the Windows CI runners instead of failing there.

## Fixes

- **Folder scans skip `gifs/`** ([#37](https://github.com/z3r0fidev/redd-media-clipper-upscaler/issues/37)).
  A Reddit MP4 (`gif --format mp4`) written to `gifs/` was picked up as a source by the next
  `clip`, `gif` or `upscale` of the parent folder. Every folder scan now skips `clips/`,
  `upscaled/` and `gifs/`. The desktop app's **Add folder** skipped none of them before; it now
  skips all three.

- **Security: a planted `ffmpeg` is refused.** An `ffmpeg` or `ffprobe` found on `PATH` inside
  the current folder is no longer used, and the version check runs with a cleared environment.
- **Security: tool probes** (`--version` checks) run through the same process handling as every
  other tool, with a timeout.
- **Security (desktop): output paths are confined.** An output path with `..` or `.` steps is
  refused, so it cannot leave the chosen folder. Videos that only an opened manifest names can
  still be read, but no longer allow writing next to them: their clips need an output folder
  picked in Settings.

## Breaking Changes

None. Fast and accurate clips, upscales and GIFs, their JSON and their exit codes are unchanged;
0.3.0 manifests and settings files read the same. A settings file that uses `"smart"` is ignored
by 0.3.0 as a whole ([Configuration](../administration/configuration.md#defaults-object)).

## Known Issues

| Issue | Effect |
|---|---|
| Smart cut handles H.264 only | HEVC, AV1 and VP9 sources are cut in accurate mode (`codec`). HEVC smart cut is a possible later feature |
| Variable-frame-rate recordings always fall back | Many phone and screen recordings are VFR, so they are cut in accurate mode (`vfr`) |
| The desktop mode choice for one video appears only once the video is in the queue | Set Smart as the default in Settings to see the bands before adding the first clip |
